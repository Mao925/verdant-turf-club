# VERDANT — 馬主ゲーム

愛馬を選び、人に託し、長い年月をかけて目標へ挑む一人用のスポーツ経営ゲーム。PC中心、スマートフォンでは経営と軽量表示を使う。Vite・React・TypeScript、既存Three.js、Supabase Free・Googleログインを採用する。

設計と進捗の正本はVaultの `スポーツ経営ゲーム/馬主ゲーム/` と `スポーツ経営ゲーム/PROJECT.md`・`WORKLOG.md`。13回答を反映した設計v0.4に従う。初回の試作URLはP2後、繁殖・親子2世代・死亡を含む正式版はP6後。

## 現在の範囲

P4までの実装は主要5場の通年番組、芝4路線・ダート2路線、収得賞金によるクラスと選出、12名のNPC馬主と継続する競走馬、最大12頭の所有・個別相談・合算予算を扱う。年1,036競走（実在重賞40＋ゲーム編成の一般競走996）を用意し、一般競走・将来年の日程と費用・能力係数はゲームの仮定として区別する。3Dは5場の数値条件と左右回りを反映する共通の簡略造形。

既存P1/P2/P3の経歴は明示的な操作で引き継ぎ、暦・愛馬・台帳・途中の相談や競走を保持する。P2は2026-09-09のユーザー完了報告で受入済み。P4では診療・療養・復帰断念・死亡、転厩・売却・引退預託、支払猶予と終了、人物との記憶を追加した。P5は繁殖と親子2世代、P6は正式公開の検証を予定する。

旧馬券版 `verdant-turf-v1` は読み取りと書出しだけに使い、コインを円へ移行しない。元コードはGitのbaselineコミットに保全する。

## 実行

Node.js 22.12以上。`npm ci` の後、`.env.example` を元に `.env.local` を用意する。VITE変数は公開されるため、Supabaseの公開用キーだけを設定する。Googleのクライアント秘密鍵・service_role・DBパスワードを置かない。

```sh
npm ci
npm run dev
npm run typecheck
npm test
npm run build
npm run test:e2e
```

未設定時はログイン設定の案内を表示し、クラウド保存ができるふりをしない。接続先を設定してからGoogleログインを行う。PKCEの戻り先は同じ配信元のルートで、固定の許可URLに登録する。

## Supabaseの設定

1. 自分のSupabase組織にゲーム専用のFreeプロジェクトを作る。有料化は別判断。
2. `supabase link --project-ref <ゲーム専用ref>` の後、`supabase db push --dry-run` で確認し、`supabase db push` でSQLを順に適用する。接続情報のキャッシュはGit除外。既存ゲーム外のテーブルは変更しない。
3. Google CloudにWeb用OAuthクライアントを作り、SupabaseのGoogleプロバイダーにIDと秘密鍵を登録。Googleの許可リダイレクトにはSupabaseが表示するcallback URLを使う。
4. Supabase AuthのSite URLと許可リダイレクトに開発用・固定試作用URLを登録。アプリの`.env.local`にはプロジェクトURLと公開用キーを設定する。
5. 実際のGoogleアカウントでログインし、別ブラウザで再開。他人のアカウント、通信断、2端末競合、書出しと取込を確認する。

P2の検証後、既存Vercelプロジェクトの固定URLを試作に使う。Supabaseの固定リダイレクトを設定し、プレビューで確認してから反映する。新規の有料サービスは追加しない。

## バックアップと検証の区別

自動クラウド保存と端末の未送信保護に加え、検証付きJSON書出し・復旧候補としての取込を行う。クラウド内の旧版はDB全体の障害に対する別バックアップではない。FreeのDB休止・容量・別途バックアップを受け入れる。配信前に運用用の暗号化保管先と定期的なDB書出し・復元手順を確認する。

`npm test` はドメインと保存制御、`npm run test:e2e` はPC・390pxの画面、IndexedDBと障害注入による再開・競合・復旧、`npm run test:db` はDockerの専用一時PostgreSQLによる全マイグレーション・権限・原子性・再送・同時更新を検証する。実サービス検証と本人のGoogleログインは区別してVaultへ記録する。Chromeの試験専用コンテキストを使い、普段のブラウザのプロファイルは使わない。

`npm run measure:p3` は4頭所有・NPC世界を365日進め、日/月送り、保存量、実際の送信差分を `artifacts/` へ記録する。`python3 scripts/measure-season-db.py` はその差分を一時PostgreSQLへ再生し、3件のチェックポイントを含めたDB割当量を測る。`npm run measure` / `measure:p2` は以前の段階用。

## 既存資産

Three.jsでコード生成した馬・騎手・競馬場を再利用する。既存の `simulation.js` は短い観戦用の旧計算であり、正式版の実在距離・時計を検証済みとはしない。`scene.js` と旧テストは接続時の回帰検証用として維持する。

## 試作の遊び方と配信

1. Googleログイン。新しい経歴では馬主名・勝負服色・初期資金・毎年1月の拠出・夢を設定する。
2. 4頭の所見を比較して入札上限と理由を記録。不成立なら別候補か14日後の市場へ。落札後は命名し支払・引渡しを完了する。
3. 佐伯修司（月70万円）か三原葵（月85万円）へ預託。日付を進め、ゲート試験後の相談で出走・見送り・路線変更を選ぶ。
4. 登録→選出→競走→精算→次の相談を繰り返す。PCの3Dとスマートフォンの軽量観戦は同じ保存済み結果の再生。早送り・スキップで賞金は変わらない。
5. 資金と契約で口座・債務・引当・12か月の賞金ゼロ予測を確認。記録室から判断の理由や競走結果を読み返し、JSON書出し・復旧を使う。

既存P1/P2/P3では「愛馬の生涯へ引き継ぐ」を使う。取得・預託待ちや未精算も保持する。旧競走はP2の確定条件で完了させ、新しい登録からP3番組を使う。旧戦績から収得賞金を再構成するが現金を再加算しない。元の競走記録がないNPCの過去実績は勝数から仮換算する。

「愛馬と予定」で馬を選ぶと相談・路線・目標が切り替わる。「もう一頭を探す」で追加取得でき、各厩舎6頭・全体12頭まで。未決の相談・未精算結果を全頭分処理してから暦を進める。同一競走の複数愛馬はまとめて精算し、観戦中の追跡馬を変更できる。番組表は月・場・路線・クラスで絞り、選出条件を確認する。有馬記念・ダービー等も条件を満たせば登録できる。

現在の番組は2099年まで。一般競走は5場を巡回する架空編成で、夏季の実際の開催分布・全JRA競走を再現しない。2歳長距離志向馬は芝2,000mから始める。初出走15日・既走10日の在厩とゲートを確認し、出走間隔14日、締切7日前・選出3日前、輸送費15万円、参加手当50万円などはゲーム設定。死亡・引退・繁殖は後続段階。

Vercelの既存プロジェクト `verdant-turf-club` を使う。公開環境変数は `VITE_SUPABASE_URL` と `VITE_SUPABASE_PUBLISHABLE_KEY` のみ。`.vercelignore` で環境・DB接続キャッシュ・運用スクリプト・検証生成物を除外。`npx vercel deploy --prod --skip-domain` で候補を作り、検証後 `npx vercel promote <deployment-url>` で固定URLへ反映する。SupabaseのSite URL/許可URLは固定試作用URLと開発用URLを維持し、Googleのcallbackは同じSupabaseのまま。

## 実サービス検証と運用の入口

- `npm test`：P1・P2・P3のドメインと保存制御、旧3D/計算の回帰。
- `npm run test:e2e`：Googleへの認証開始パラメータ、PC・390pxの全判断、モックAPIで通信断・応答消失・競合・復旧・P1移行。実サービス用1件は既定でスキップ。
- `node --env-file=.env.local scripts/live-cloud-check.mjs`（公開URLを検証する場合は環境変数 `P2_BASE_URL=https://verdant-turf-club.vercel.app` を指定）：実Supabaseで一時ユーザーを作成し、発行されたテストセッションで実RPC・画面の取得/競走/通信断/応答消失/競合/復旧・他人の行が見えないことを検証。メールを送信しない。終了時に一時アカウントとそのセーブを削除する。これは実Google認証とは区別する。トレース・動画・画面の自動保存は無効。
- `npm run test:db`：TCPで起動完了を確認した隔離PostgreSQLに全マイグレーションを適用し、権限・原子性・二重送信・同時更新を検証。
- `npm run measure:p2`：一頭と永続NPCを3歳8月末まで進める合成負荷。`npm run measure` は従来のP1長期負荷。
- `npm run backup`：既存MacキーチェーンのSupabase CLI認証でゲーム4表と認証利用者のIDだけを取得し、暗号化＋HMACを付けて `~/Documents/Backups/verdant-owner/` へ保存。平文・トークンはログやファイルへ出さない。Python 3、既存のcertifi、openssl、Macのsecurityコマンドが必要。
- `python3 scripts/backup-cloud.py --verify <file.vbackup>`：HMACと復号、ゲームの整合性を確認し、一時PostgreSQLへ4表を復元して件数・参照を検証する。DockerとNodeが必要。本番へ書き戻さない。

このMacに `local.verdant-owner.backup` の日次09:00ジョブを登録。Macが利用可能なときに動く。ログは `~/Library/Logs/verdant-owner/`。実行前にも手動バックアップを行う。暗号鍵はキーチェーンの `Verdant Owner Backup` / `verdant-owner` に保管し、Vault/Gitへ複製しない。暗号化ファイルと鍵の両方が必要。これだけで別拠点の災害対策やSupabase Auth全体の復元を保証しない。

実DB復旧時はまず別環境で `--verify` を通す。同じ認証ユーザーIDを維持したSupabaseへゲーム4表の内容を復元する手順と、現在のセーブを保護した上でゲーム内JSON復旧する手順を区別する。現在の本番データに対する一括置換はこのスクリプトでは行わない。ユーザーの操作記録・面白さ・実Googleの確認はVaultの各段階の記録へ残す。

## P3の長期保存を実サービスで確認する

`P3_LIVE_WORLD=artifacts/p3-year-world.json node --env-file=.env.local scripts/live-cloud-check.mjs` で、通常の実RPC障害検証に続いて一年分の合成世界を一時アカウントへ4回明示復旧し、読込み・ブラウザ再開を検証する。固定URLを対象にするときは `P2_BASE_URL=https://verdant-turf-club.vercel.app` も指定する。本人のセーブに書き込まない。1年世界の保存3.93MB、増分2.35MB、年間アップロード15.33MB、一時DBのゲーム4表の割当16.56MBを計測。端末・通信・人数を含む上限保証とはしない。人数別の無料枠見積りと証拠はVaultのP3実装記録に置く。

## P4の実装範囲

P4は健康エピソード（競走・調整・放牧中の外傷と疝痛）、初期対応・診断・追加所見・療養再評価・復帰/競走復帰断念・死亡、外部休養と引退預託、転厩、買い手探し/提示/合意/引渡しを伴う売却、支払猶予と活動終了、人物との場面と年表を加える。P3までの経歴は明示的に引き継ぐ。生命予後を費用や成績から決めず、死亡後の予定と契約を止め、既発生債務・血統・成績を残す。現実の医療助言や正確な発生率の再現ではない。率・期間・料金は根拠と仮定を区別し、数年の負荷と感度分析を記録する。P5繁殖・親子2世代、P6正式公開の必須範囲は維持する。

P4の操作：愛馬ページの「診療とこれからの生活」で診断報告、療養・帰厩・引退預託・売却を選ぶ。「人物と愛馬の記憶をたどる」で馬・年を選び、相談や診療の根拠と任意の言葉を読み返す。死別後も個体・戦績を保持する。資金ページで支払猶予や活動終了時の残る債務と飼養先未解決を確認する。健康率・予後・費用の仮定と校正残件はVaultのP4健康モデル資料を参照。

P4検証：`npm run measure:p4` で4頭・1,096日を進める。`npm run measure:health` で原因別ハザードを100万出走／100万日×0.5/1/2倍で確認。`python3 scripts/measure-life-db.py` で3年の差分を一時DBへ再生。`P4_LIVE_WORLD=artifacts/p4-three-year-world.json node --env-file=.env.local scripts/live-cloud-check.mjs` で実クラウドの診療・療養と3年世界の復旧・再読を一時アカウントで検証。公開時は `P2_BASE_URL` に既存固定URLを指定する。
